## Context

参见 `proposal.md` 的 Why。当前 `TrafficService` 有两条获取路径：异步主流程通过 `_fetch_rules_from_api()` 返回 `TrafficRule`，同步兼容流程通过 `_fetch_limit_rules_sync()` 返回旧 API 字典；两者最终都依赖已经失效的 JSON 接口。限行缓存按日期存储，并要求 `limited_time` 使用中文日期格式。

北京交管详情页以 HTML 表格提供多个轮换日期区间，并在内嵌脚本中维护节假日清单。页面本身不提供可复用的限行 JSON API。

## Goals / Non-Goals

**Goals:**

- 在主 JSON 接口失败后，从官方详情页提取可验证的每日限行规则。
- 让异步主流程和同步兼容流程得到一致结果。
- 复用现有 `TrafficRule`、缓存键格式和错误处理边界。
- 不增加第三方依赖，并让来源在日志或服务状态中可识别。

**Non-Goals:**

- 不执行官网 JavaScript，不使用浏览器自动化。
- 不替换当前主 JSON 接口的优先级。
- 不推断轮换表覆盖范围之外的日期。
- 不新增用户可配置的 URL、数据库表或后台任务。

## Decisions

### 1. 解析 HTML 表格，不执行 JavaScript

使用 Python 标准库 HTML 解析能力，按表头 `轮换日期 / 星期` 定位目标表格，再读取日期范围和五个工作日单元格。

备选方案是引入 BeautifulSoup 或运行 Playwright。前者增加运行时依赖，后者增加浏览器和部署成本；页面数据已在 HTML 中，二者都没有必要。

### 2. 表格为主，Holiday 数组为覆盖

轮换表负责提供周期性星期映射；内嵌 `Holiday` 数组负责覆盖法定节假日。解析器将日期范围展开为每日规则，周末及清单中的节假日设为“不限行”。

备选方案是只提取页面顶部的 `#jsStr2`。该区域只展示今天和明天，并依赖客户端日期，无法满足一周查询和缓存预热，因此拒绝。

### 3. 以 `TrafficRule` 作为内部规范格式

页面解析结果先转换为现有 `TrafficRule` 列表。异步路径直接使用该列表；同步兼容路径再转换为其既有的 `limitedTime`、`limitedNumber` 字典格式。

备选方案是让页面解析器直接返回两种格式，会重复日期和来源逻辑，增加异步与同步结果分叉的风险。

### 4. 保持缓存优先和主接口优先

查询顺序保持为：现有缓存 -> 主 JSON 接口 -> 官方详情页。页面解析成功后使用现有缓存写入流程按日期缓存，不改变缓存键和 TTL 规则。

主接口失败后的页面访问只作为降级，不在缓存命中时额外访问官网。

### 5. 固定官方详情页地址

将官网详情页作为代码内固定备用地址，与当前主接口地址保持同类处理，不新增配置项。

备选方案是增加配置项，虽然更灵活，但对只有一个官方备用来源的场景增加配置校验、模板和迁移负担。

### 6. 来源显式标记

页面生成的规则使用独立的来源标识，例如 `official_page`；服务状态保留现有主地址兼容字段，并补充备用地址或最终来源信息。

这样可以在主接口恢复前确认提醒使用的是哪个来源，而不改变已有调用方的规则字段。

## Risks / Trade-offs

- [官网 HTML 结构改版] -> 解析器按表头和列数校验，结构不符合预期时整体失败并记录日志，不返回部分猜测结果。
- [页面只公布有限日期范围] -> 目标日期超出范围时明确返回无规则；继续依赖已有缓存或后续官网更新，不自行外推。
- [节假日清单遗漏或更新滞后] -> 将页面清单视为唯一覆盖依据，并在来源日志中保留页面解析结果；不引入另一套本地节假日表造成冲突。
- [同步与异步格式转换不一致] -> 使用同一个 `TrafficRule` 中间格式，并为两条路径增加等价性测试。
- [主接口当前重试较多] -> 页面降级发生在主接口重试耗尽后，保持现有稳定性策略；后续若延迟可观测地过高，再单独调整重试预算。

## Migration Plan

1. 部署包含解析器、降级调用和单元测试的版本；不需要数据迁移或 Redis 清理。
2. 主接口恢复时，缓存命中或主接口成功仍沿用现有路径。
3. 若官网页面解析出现问题，回滚应用版本即可；旧缓存键和主接口调用保持兼容。
